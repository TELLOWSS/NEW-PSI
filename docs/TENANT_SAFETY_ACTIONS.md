# 기업별 안전조치 관리

2026-09-30. `/saas/access`에서 개인 계정과 활성 기업 소속으로 새 안전조치를 관리한다. 기존 현장 자료의 자동 이관은 없으며 전체 프로그램의 공용 SaaS 전환은 아직 완료되지 않았다.

## 업무 흐름

- owner/admin/reviewer는 조치를 등록하고 미착수 → 진행 중 → 검토 요청으로 변경한다.
- owner/admin만 검토 요청 건을 완료 처리하며 5자 이상의 확인 내용을 남긴다. 완료 건은 잠기며 관리자가 사유를 입력해야 다시 연다.
- viewer는 자기 기업 자료와 변경 이력만 조회한다. 삭제와 이력 수정 경로는 제공하지 않는다.
- 기업 전환·로그아웃·접근 거부 시 화면 자료를 정리한다. 세션은 메모리에 보관하고 늦게 도착한 이전 기업 응답을 폐기한다.

## 서버와 DB

기존 `/api/saas/access?resource=actions`에서 GET/POST/PATCH를 처리하므로 Vercel 함수는 4개를 유지한다. 매 요청마다 Supabase Auth 사용자와 활성 소속을 확인하며 사용자 JWT의 RLS 클라이언트를 사용한다. 기업 ID·작성자·권한은 요청 본문으로 정할 수 없다.

등록은 UUID `requestId`로 같은 사용자의 동일 입력 재시도를 처리한다. 수정은 `id`와 `expectedRevision`을 함께 요구하며 오래된 수정 요청은 409로 거부한다. 목록은 25건씩 커서로 조회하며 상세 이력은 최근 100건까지 표시한다.

마이그레이션 순서는 `20260929000000_tenant_identity_foundation.sql`, `20260930000000_tenant_safety_actions.sql`이다. 네 테이블 모두 RLS를 활성화·강제한다. DB 트리거가 역할·상태 전환·작성자·수정 번호를 검증하고 같은 트랜잭션에서 감사 이력을 기록한다. 감사 기록이 실패하면 업무 수정도 롤백한다.

사용자가 지정한 Supabase 프로젝트 `dpnmslogvwuzmighsgnt`에 두 마이그레이션을 적용했다. 신규 기업·소속을 임의 등록하거나 기존 자료를 귀속하지 않았다. 기업 이름과 실제 Auth 사용자 UUID에 대한 운영자의 명시적인 소속 등록이 필요하다. 서비스 키와 비밀번호를 문서나 채팅에 기록하지 않는다.

## 검증과 남은 범위

Node 22의 `verify:ci`: 86개 파일, 688개 테스트, 타입 검사·보안 검사·빌드 통과. PostgreSQL 정책 테스트는 양방향 기업 격리, 조회자·검토자 제한, 완료 확인, 재개 사유, 위조·삭제 차단, 정지 소속 차단, 수정 충돌, 등록 중복, 감사 실패 시 원자적 롤백을 검증한다.

호스팅 DB 확인용 SQL은 `supabase/tests/tenant_identity.sql`과 `supabase/tests/tenant_safety_actions.sql`이다. 가상 자료를 트랜잭션 안에 만들고 전부 롤백한다. 실제 사용자 로그인→기업 선택→등록→관리자 확인까지의 운영 검증은 실제 계정과 소속을 준비한 후 별도로 수행한다.

기존 업무 테이블·근로자 공개 링크·첨부 저장소의 기업 분리는 남아 있다. `PSI_DEPLOYMENT_MODEL=shared-saas` 출시 차단을 유지한다. 신규 테이블의 RLS만으로 기존 데이터가 기업별 보호되는 것은 아니다.
