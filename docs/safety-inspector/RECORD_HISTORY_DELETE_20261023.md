# 점검기록 목록 삭제와 정리 — 2026-10-23

## 목적과 사용 흐름

사진 점검 첫 화면의 ‘저장 기록 · 상세 관리’ → 자동으로 불러온 점검기록 → 해당 기록의 ‘삭제’ → 대상·범위 확인 → 확인 체크 및 최종 확인 → 서버 잔여 검증 → 검증서 저장 또는 닫기.

기존 삭제는 보고서 탭 안에만 있어 기록 정리 시 여러 단계를 거쳐야 했다. 목록의 열기와 삭제를 별도 버튼으로 분리하고 제목·점검번호·버전을 표시한다. 초보자는 삭제할 기록을 먼저 열거나 보고서를 만들 필요가 없다. 여러 기록을 한꺼번에 지우는 기능은 이 범위에 포함하지 않는다.

## 구현과 데이터 경계

- 기존 `delete-inspection` / `deletion-status` 및 서버 Storage 제거·기존 서명 링크 만료 대기·DB 정리·잔여 검증 엔진을 재사용한다. DB migration, RLS, 인증, 환경변수, 의존성 변경이 없다.
- ‘전체 삭제’는 사진·설명·분석·이력·고정 보고서 전체를 대상으로 한다. ‘사진 파일만’은 DB 기록과 보고서를 유지하며 편집을 잠근다. 두 범위를 구별하고 사진만 삭제 후 전체 삭제 전에는 확인 체크를 다시 받는다.
- 서버의 `verified`와 명시된 삭제 범위가 확인된 뒤에만 목록을 제거한다. 파일 0건, 목록 조회 실패, 응답 유실만으로 성공 처리하지 않는다. 검증서에는 확인 시점의 서버 상태와 잔여 건수를 담는다.
- 처리 중 중복 실행과 확인창 닫기/Escape를 차단한다. 링크 만료 대기 중에는 닫을 수 있다. 창을 열어 둔 명시적 삭제만 기존의 일회 자동 마무리를 사용하며, 닫기·새로고침은 삭제 요청을 예약하거나 자동 재시도하지 않는다.
- 같은 탭의 sessionStorage에는 삭제를 실제 요청한 점검의 UUID와 revision만 저장한다. 제목·사진·분석·비밀번호는 저장하지 않는다. 기록이 이미 목록에서 사라졌거나 응답이 끊겼어도 ‘삭제 상태 확인’으로 서버 결과를 읽고 미완료 작업을 재시도할 수 있다. 탭 종료 시 이 위치 정보도 사라진다. 다른 기기에서는 해당 기록의 삭제 관리로 확인한다.
- 저장 전 변경사항이 있으면 목록의 삭제를 막는다. 현재 열어 둔 기록이 삭제되면 사진 URL·선택·보고서 화면을 정리하고 전체 삭제 시 편집 문서를 닫는다. 다른 기록을 삭제해도 현재 문서는 바꾸지 않는다.
- 첫 목록을 자동 조회하고 검색·필터와 함께 최근 등록순 / 최근 수정순 / 긴급·미결 우선을 제공한다. 정렬은 불러온 부분집합에만 적용하며 서버의 등록일+UUID 페이지 커서는 유지한다. 표시 수 / 불러온 수 / 이전 기록 유무를 구별한다.
- 모바일에서 목록을 환영 화면보다 앞에 배치하고, 삭제 버튼 최소 44px·확인창 고정 헤더·내부 스크롤·닫은 뒤 포커스 복원을 적용한다. 목록/삭제 확인은 사진·분석 원문 다운로드나 유료 AI 호출을 발생시키지 않는다. 상태는 사용자의 조회 및 대기 후 일회 재시도만 사용하며 초 단위 서버 폴링을 추가하지 않는다.

## 공식 기준 확인

Supabase 공식 [Delete Objects](https://supabase.com/docs/guides/storage/management/delete-objects)는 SQL로 storage 메타데이터만 삭제하면 실제 객체가 남으므로 Storage API의 remove를 사용하도록 안내한다. 기존 서버 구현은 이 방식을 유지한다. 2026-10-23에 changelog.md의 Storage 및 breaking change 항목을 확인했다. 2026-11-10 예정 구형 TLS 1.2 cipher 중단은 이번 UI 변경이나 현행 서버 SDK 경로의 변경을 요구하지 않는다.

기기 원본·이미 내려받은 PDF·클립보드·외부 AI·공유 사본·제공자 백업/로그까지 삭제했다고 표현하지 않는다. 무료 저장소와 DB 표시량은 즉시 줄어들지 않을 수 있고 이미 사용한 전송량은 삭제로 환급되지 않는다. 최소 삭제 영수증은 재시도 확인용으로 남는다.
