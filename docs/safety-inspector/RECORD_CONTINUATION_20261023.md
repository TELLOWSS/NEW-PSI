# 저장 점검에서 바로 이어 처리 — 2026-10-23

## 문제와 목표

기록 목록은 저장본을 찾고 지우기에는 충분하지만, 사진 검토나 개선사진·재점검을 이어가려면 상세 단계 또는 간편 화면에서 다시 위치를 찾아야 했다. 저장 기록마다 이어보기 하나를 제공해 남은 업무로 바로 이동한다. 여러 점검을 다루는 전문가가 다른 점검의 사진·조치와 혼동하지 않도록 점검명·저장 버전·범위를 표시한다.

## 동작

| 저장 목록 상태 | 이어보기 | 최신 저장본에서 실제로 하는 일 |
| --- | --- | --- |
| AI 사실 검토 대기 있음 | 검토 이어보기 | 사진 순서상 첫 미검토 분석의 사진 1장과 저장 결과를 읽어 표시 |
| 검토 대기 없음, 미결 조치 있음 | 조치 이어보기 | 등록 조치 화면을 열고 ‘미결 전체’·기한순으로 표시 |
| 둘 다 없음 | 간편 화면 열기 | 사진·조치 자료를 간편 화면으로 읽어 표시 |

조치 이어보기에서는 검색·필터 도구를 접어 두어 첫 미결 조치를 먼저 보여주고, 필요할 때 도구를 펼친다. 기존 기록 본문 클릭은 상세 편집을 유지한다. 저장 전 수정이 있으면 이어보기 버튼을 비활성화한다. 요약이 오래됐더라도 상세 문서를 다시 읽어 실제 검토 대기 사진을 고른다. 이미 검토가 끝났으면 그 사실을 안내하고 임의로 다른 사진을 분석하거나 검토 완료로 표시하지 않는다.

‘미결 전체’에는 미조치와 완료 검토 요청을 함께 포함하고 현장 재점검 확인된 조치는 제외한다. 검색·페이지·요청문·기한 정렬의 기존 기능과 함께 사용한다. 오늘 기한은 지연으로 세지 않고 한국시간 기기 시계 기준을 유지한다. 사진이 없는 이전 조치 기록도 등록 조치 조회는 가능하다.

## 보관·비용·실패 처리

- 새로운 API/DB schema·RLS·저장소·환경변수·의존성 변경이 없다. 기존 list/detail/photo/deletion-status 읽기 경로를 사용한다.
- 목록은 제목 등 요약만 읽는다. 조치 이어보기·간편 열기는 사진을 미리 내려받지 않는다. 검토 이어보기는 선택한 미검토 사진 1장만 읽고 기존 SHA-256으로 무결성을 확인한다.
- 생성·업로드·재분석·사실 수용·완료 확정·보고서 작성·삭제·공유 발송은 자동으로 실행하지 않는다. AI 분석 키와 요청 식별자도 변경하지 않는다.
- 선택 점검번호는 화면 상태로 전달한다. 기존 탭의 마지막 점검번호가 다른 점검을 가리켜도 선택 점검만 연다. 세션의 마지막 점검 위치는 성공적으로 읽은 뒤에만 갱신한다.
- 읽기 실패 시 자동 반복하지 않고 선택 점검의 재시도 버튼을 제공한다. 삭제 대기·사진 삭제된 기록에는 사진/조치 진입을 막고 기존 보관·삭제 관리로 안내한다. 이미 전체 삭제된 기록은 서버 verified 확인 후 삭제 결과 관리로 연결한다.
- 사진 정보가 없거나 파일 해시가 다르면 결과를 표시하지 않고 오류를 알린다. 저장 문서·기존 보고서를 고치거나 다른 사진을 대신 붙이지 않는다.
- 저장 사진의 검토 입력 중 기록 목록으로 이동할 때도 저장 전 의견 유실 확인을 받는다. 개발 StrictMode의 폐기된 mount는 자동 읽기를 시작하지 않도록 정리 가능한 초기 예약을 사용한다.

## 검증 범위

`inspectorRecordResume.test.ts`는 이어보기 우선순위, 목적지·번호 검증, 최신 문서의 미검토 범위, 수용/반려/수동 사진 제외, 미결 전체의 검색·기한 정렬과 원문 불변을 검증한다.

`verify-inspector-resume.mjs`는 실제 UI·production CSP에서 검토/조치/간편 이어보기, 오래된 요약, 빈 기록, 사진 없는 이전 조치, 삭제 잠금, 보관 정보 누락, 사진 해시 오류, 선택 점검 재시도, 이미 삭제된 기록, 저장 전 변경 보호를 검증한다. 사진 요청 범위·불필요한 사진 다운로드·업무 쓰기 0·유료 AI 호출 0·문서 불변·모바일 가로 넘침도 검사한다. 업무 API fixture와 실제 운영 읽기 검증은 구별하여 연결 PR에 기록한다.
