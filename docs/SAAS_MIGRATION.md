# 공용 SaaS 전환 현황과 이관 절차

2026-09-30. 목표는 여러 기업이 함께 사용하는 공용 SaaS이다. 현재 앱의 기업별 데이터 분리는 **미완료**이며, 이번 변경은 인증 강화·출시 검사·기업 권한 DB 기반을 제공한다. 공용 운영 승인이나 실제 DB 이관을 뜻하지 않는다.

## 검증 결과

- Node 22: 전체 86개 테스트 파일, 688개 테스트 통과.
- `verify:fast`(타입 검사 포함) 통과, 운영 Vite 빌드 통과.
- 의존성 갱신 및 PGlite 추가 설치 시 npm audit 취약점 0건.
- 브라우저에서 개인 계정 화면 표시와 설정 누락 시 로그인 비활성화 확인.
- 기업 권한 기반과 신규 안전조치 테이블을 사용자가 지정한 Supabase 프로젝트에 적용했고 호스팅 DB의 기업 격리·완료 권한·감사 이력·정지 소속 차단을 롤백 검증했다. 실제 계정과 기업 소속을 이용한 운영 업무 흐름 및 기존 자료 이관은 남아 있다.

신규 기능의 역할·운영 절차·남은 범위는 [기업별 안전조치 관리](TENANT_SAFETY_ACTIONS.md)를 참조한다. Vercel 함수 4개 구조를 유지한다.

## 이번 변경

- 세션 서명키를 `ADMIN_SESSION_SECRET`으로 분리했다. 공개 환경변수와 API 토큰으로 세션을 서명하지 않는다.
- 잘못된 쿠키 인코딩·서명 형식·발급/만료 시간을 거부한다.
- 운영 화면에서 개발용 우회를 비활성화한다. 저장된 우회 값도 운영 로그인에 전달하지 않는다.
- `VITE_PSI_ADMIN_SECRET` 서버 폴백을 제거했다. 기존 공개 키는 운영자가 폐기·회전해야 한다.
- 기존 계산식을 유지하면서 `개선 이행률` 표시를 `응답 기반 개선 신호`로 바꿨다. 실제 조치 완료율로 해석하면 안 된다.
- 의존성 보안 갱신, 잠금파일 기반 설치, Node 22, GitHub 검증 workflow, Vercel 빌드 전 테스트·타입 검사·취약점 검사를 추가했다.
- `psi_tenants`, `psi_tenant_memberships`와 RLS를 추가하는 SQL을 준비했다. 지정된 Supabase 프로젝트에 적용했다. 기존 업무 테이블은 변경하지 않는다.
- `/saas/access`에 개인 계정 로그인과 소속 기업 확인 화면을 추가했다. 세션은 메모리에만 보관하며 기존 현장 자료나 관리자 로그인 상태에 연결하지 않는다.
- `/api/saas/access`는 Supabase Auth의 `getUser`로 사용자 토큰을 검증하고 활성 기업 소속을 매번 조회한다. 권한 검증에는 사용자 토큰의 RLS 클라이언트를 사용하고 서비스 키를 사용하지 않는다. 조회 응답은 캐시하지 않는다.
- 공용 모드에서는 기존 공유 관리자 쿠키·API 토큰을 서버에서 거부한다. 이 차단만으로 공개 근로자 링크 등 모든 기존 경로의 전환이 끝난 것은 아니다.

## 기업 권한 기반

`supabase/migrations/20260929000000_tenant_identity_foundation.sql`은 Supabase Auth 사용자를 기업과 연결한다. 역할은 owner/admin/reviewer/viewer, 상태는 active/suspended다. 인증된 사용자는 자기 활성 소속과 그 기업만 읽을 수 있다. 브라우저는 기업 생성·소속 변경·역할 승격을 할 수 없다. 초기 구성은 신뢰된 서버 운영자가 수행한다.

신규 테이블의 RLS는 **기존 자료를 보호하지 않는다**. service_role은 RLS를 우회하므로 현재 서버 코드에 기업 ID 필터 하나를 추가하는 것으로 전환을 완료할 수 없다. SQL 테스트는 `supabase/tests/tenant_identity.sql`에 있으며 격리된 Supabase 테스트 DB에서 실행 후 전체 롤백한다. `tests/tenantIdentitySql.test.ts`에서 PGlite의 임시 PostgreSQL로 실제 정책을 실행하여 기업 간 격리, 정지 소속 차단, 자기 권한 변경 금지, 익명 접근 금지와 테스트 데이터 롤백을 검증했다. 이 검사는 Supabase Auth의 최소 SQL 인터페이스를 재현하므로 실제 호스팅 DB·Auth·PostgREST 연결 검증은 별도로 필요하다.

## 개인 계정 확인 사용법

1. 테스트 프로젝트에 migration을 적용하고 Supabase Auth에서 운영자가 발급한 테스트 사용자 UUID로 기업/소속을 등록한다. 앱에는 자가 가입이나 권한 승격 경로가 없다.
2. 브라우저에 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`를 설정한다. 서버는 동일한 URL과 `SUPABASE_ANON_KEY` 또는 기존 공개 anon 키 설정을 사용한다. service_role 키를 이 설정에 넣지 않는다.
3. 웹과 API가 함께 실행되는 테스트 배포에서 `/saas/access`를 연다. Vite만 실행하면 화면 확인만 가능하며 `/api/saas/access`는 실행되지 않는다.
4. 이메일/비밀번호로 로그인한 후 기업을 선택한다. 서버가 확인한 소속과 역할을 표시한다. 가입·비밀번호 재설정은 현재 운영 관리자 경로를 이용한다.
5. 새로고침/로그아웃 후 재로그인을 확인하고, 운영자가 소속을 정지하면 다음 확인 요청이 거부되는지 검증한다. 이 화면은 아직 기존 업무 화면을 열지 않는다.

로컬 회귀 검사: `npm run test:ci`. PostgreSQL 정책만 검사: `npx vitest run tests/tenantIdentitySql.test.ts --maxWorkers=1`.

## 전환 완료에 필요한 순서

1. 테스트용 Supabase 프로젝트에서 위 SQL과 양방향 접근 테스트를 실행한다. 고객 기업 2개, 계정별 역할, 정지/탈퇴 사용자를 포함한다.
2. 추가된 개인 계정 확인 화면/API를 실제 테스트 프로젝트에 연결한다. 기존 업무 요청에도 검증된 사용자·기업 소속·역할을 연결한다. 기존 공유 비밀번호/`x-admin-auth`는 공용 모드에서 이미 거부하지만 업무 경로 전환은 남아 있다.
3. 업무 자료·근로자·교육·사례·원본·첨부·분석 작업·감사로그·사용량 각각에 소유 기업을 정의한다. 승인된 명시적 원본-기업 매핑, 백업과 복구 검증 없이는 기존 자료를 자동 귀속하지 않는다.
4. 업무 테이블의 기업별 RLS, 기업 포함 외래키, 파일 저장소 정책을 적용한다. 사용자 요청은 사용자 토큰의 RLS 클라이언트를 사용한다. 서비스 권한이 필요한 작업은 소속 검증과 기업 범위를 별도로 강제한다.
5. 교육/근로자 공개 링크, 일회성 토큰, 분석 작업 상태·재시도·다운로드 경로까지 기업 정보를 묶어 검증한다. 다른 기업의 ID를 넣은 읽기/쓰기/삭제/내보내기를 모두 거부하는지 테스트한다.
6. 브라우저 저장소와 캐시를 사용자·기업별로 분리한다. 기업 전환/로그아웃 시 화면 및 캐시를 정리하고 기존 로컬 자료는 소유권 확인 전 격리한다.
7. 실고객 개인정보를 AI에 전송하기 전 실제 과금 프로젝트·계약·보존·국외 처리 조건을 확인하고, 승인된 처리 경로를 코드로 제한한다. `FREE`/`PAID` 키 이름만으로 판정하지 않는다. 현재 기존 AI 경로는 이번 변경에서 바꾸지 않았다.
8. PC 보관함과 명령줄 도구의 새 백업은 암호화 저장·복원 검증을 제공한다([사용 절차](ENCRYPTED_BACKUP.md)). 기존 평문 백업과 다른 내보내기 경로는 별도 관리해야 한다. 실제 복구 훈련, 이용약관·개인정보 처리 문서, 고객 과금/사용량 제한, 운영 알림도 남아 있다.
9. 전체 접근 테스트와 실제 고객 흐름 검증 후 코드의 공용 출시 차단을 제거한다. 환경변수만으로 우회할 수 있는 승인 플래그는 만들지 않는다.

## 배포와 복구

`PSI_DEPLOYMENT_MODEL=shared-saas`는 현재 `build:verified`를 실패시킨다. 기본값 `single-site`는 기존 현장 운영과 호환하기 위한 것이며 사용자 요청의 목표 모델을 바꾸는 설정이 아니다. 공용 서비스에 기본값을 사용하여 검사를 회피하면 안 된다.

Vercel 운영 빌드는 별도 32자 이상 세션 서명키와 로그인 비밀번호를 요구한다. 공개 관리자 키나 운영 우회 설정은 배포를 차단한다. 키 값은 로그에 출력하지 않는다. Vercel 대시보드에 별도 Build Command 재정의가 있으면 저장소 설정 적용 여부를 확인한다.

GitHub의 `release-verification` 작업을 main 보호 규칙의 필수 검사로 지정해야 한다. workflow 파일 추가만으로 main 보호가 활성화되지는 않는다. 이번 변경은 저장소/서비스의 원격 설정을 수정하거나 운영 배포를 실행하지 않았다.

SQL은 새 테이블만 생성한다. 실패 시 트랜잭션이 롤백된다. 이미 적용한 뒤 되돌려야 하면 먼저 소속 정보 백업과 의존성을 확인한다. 실제 고객 계정이 추가된 테이블을 자동 삭제하는 롤백은 제공하지 않는다.
