# 백업 후 재작업 — 2차 개선

## 사용자 흐름

보관 폴더 열기 → 원문 1건 열기 → **이 기록 작업 이어하기** → 상세 화면에서 수정·저장 → 상세창 닫기 → **수정본 새 백업 저장 (1건)**.

새 작업본 JSON은 나중에 기존 **백업 파일 검증·복원**으로 다시 가져올 수 있다. 50MiB 미만 일반 JSON에 적용하며, 대용량 원본은 PC 보관함에서 필요한 기록을 선택한다. 원래 보관 폴더와 월별 원본 JSON은 변경하지 않는다.

## 보호 정책

- 같은 ID가 현재 작업 목록에 있으면 현재 작업본을 열며, 보관함의 옛 내용으로 덮어쓰지 않는다. 백업이 더 최신이어도 자동 교체하지 않으므로 내용 비교가 필요한 경우 별도 확인이 필요하다.
- 신규 작업본은 기존 복원 검증·이미지 중복 검사·저장 실패 처리 경로를 사용한다. 다른 ID의 같은 문서를 자동으로 합치지 않는다.
- 일반 백업 가져오기와 보관함 작업 재개에서 식별 가능한 과거 기록의 원점수·원등급 보존 정보를 남긴다. 이미 변환된 기록의 수동 수정은 초기 평가로 되돌리지 않는다.
- 비서명 백업의 점 구분 날짜는 실제 달력 날짜인지 확인한 뒤 작업용 사본에서만 정규화하고 원래 값과 사유를 남긴다. 서명 월마감 파일은 임의 정규화하지 않는다.
- 실제 저장 결과가 없을 때 미저장된 incoming 기록을 상세창에 표시하지 않는다.
- 새 작업본 백업은 선택한 기록의 **프로그램에 저장된 상태**만 포함한다. 편집창의 미저장 입력은 포함하지 않는다. 다운로드 완료 여부는 브라우저/저장 폴더에서 확인해야 한다.
- 새 작업본 파일명에 저장 시각을 포함한다. 기존 보관함에 덮어쓰지 않는다.
- 작업 재개만으로 OCR·유료 API·월마감 서버 영수증 등록을 실행하지 않는다. 별도의 재분석은 기존 비용 승인 정책을 따른다.

## 범위와 제한

새 보관함에서 운영으로 가져오는 기능과 수정본 다운로드는 **1건 단위**다. 다수 기록의 작업세트 버전 관리, 자동 재개, 전체 운영 DB의 메모리 경량화까지 완료된 기능은 아니다. 이미 운영 DB에 누적된 대용량 이미지로 인한 메모리 문제도 남아 있다. 원문 폴더에는 읽기 권한만 요청하며, 다운로드 경로는 브라우저 설정을 따른다.

## 검증

- 76개 테스트 파일 / 587개 테스트 통과.
- TypeScript, verify:fast, 배포용 빌드 통과.
- 분리된 Chromium / 합성 자료: 보관 생성 → 작업 재개·저장 → 새 백업 다운로드 → 다른 빈 브라우저 컨텍스트에서 다운로드 파일 복원 → 원문·날짜·등급 확인 → 기존 작업본 재열기(재가져오기 확인창 없음) 통과.
- 편집창을 통한 모든 수동 수정 UI를 자동 검사한 것은 아니다. 수동 수정 값의 보존은 별도 단위 테스트로 확인했다.
- 브라우저 스크린샷 단계에서 긴 패널 캡처 후 요소 탐색이 실패한 실행이 있어, 상호작용 완료 후 뷰포트 캡처로 분리했다. 최종 실행은 전체 흐름과 원문 닫기까지 통과했다.
- 실제 사용자 운영 데이터에 가져오기·삭제·유료 OCR을 실행하지 않았다. 이번 소스는 로컬 반영이며 배포 여부는 별도 확인한다.
