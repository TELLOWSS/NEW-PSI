# PC 저메모리 보관함 — 1차 구현

## 목적

월별 백업을 모두 운영 DB와 React 상태에 합쳐 넣지 않고 PC 폴더에서 조회한다. 173MB JSON 복원 중 발생한 브라우저 메모리 부족에 대응하는 별도 보관 경로다. 기존 운영 데이터의 getAll 로딩과 누적 메모리 문제까지 해결한 것으로 보아서는 안 된다.

## 사용

위험성평가 분석 → 운영·백업 → PC 저메모리 보관함 · 원본 보존.

1. 월별 원본 JSON을 선택한다.
2. 새 PC 보관함 만들기에서 저장할 상위 폴더를 선택한다. 고유 이름의 새 하위 폴더에만 쓴다.
3. 완료 메시지를 확인하고 원본 JSON도 별도로 보존한다.
4. 이후 보관 폴더 열기에서 해당 하위 폴더를 연결한다. 목록에는 20건씩 표시하며 원문과 이미지는 선택한 기록만 읽는다.

폴더 전체를 이동·백업해야 한다. index.json만 복사하면 증빙은 따라오지 않는다. Chrome/Edge의 폴더 접근 기능이 필요하며 사용자 권한 승인을 우회하지 않는다. 평문 보관이므로 개인정보 접근 제한 및 디스크 암호화 등 PC 관리가 필요하다.

## 저장 구조

```text
PSI-보관-날짜-고유번호/
  STARTED.json        시작 표시 — 이것만 있으면 미완료
  source-envelope.json 원본 JSON 최상위 메타데이터 (기록 배열 제외)
  records/
    000001.json       원본 기록 필드 전체, 이미지 포함
    000002.json
  index.json          가벼운 목록·기록별 SHA-256 — 최종 검증 후 마지막에 생성
```

- 원본의 점수·등급·날짜·수기·이미지·추가 필드를 재계산하거나 삭제하지 않는다.
- JSON framing과 서명 월마감 manifest 검증을 공용 스트리밍 파서에서 완료한다.
- 한 기록씩 파싱하고 파일 쓰기 완료를 기다린다. 전체 이미지 배열은 반환·유지하지 않는다.
- 저장 후 기록별 크기와 SHA-256을 재대조한다. 목록을 다시 열 때는 형식을, 기록을 열 때는 실제 내용을 대조한다.
- 체크섬은 우발적 변경 탐지이며 디지털 서명·접근통제·OCR 정확도 인증을 대신하지 않는다.
- 중단·저장 실패 시 원본과 미완료 폴더를 그대로 두며 기존 데이터를 삭제하지 않는다. 재개 기능은 아직 없으므로 새 보관함으로 재시도한다.
- 한 기록 32MiB, 보관함 1개 1만 건, 목록 8MiB 한도. 전체 PC 메모리 사용량의 보장치는 아니다.
- 운영 DB, 서버, 유료 OCR에 쓰지 않는다. 날짜 점 구분 형식도 원문 그대로 보관한다.
- 50MiB 이상 운영 JSON 가져오기는 선제 차단하고 새 보관 경로를 안내한다. 50MiB 미만도 누적 환경에서 무조건 안전하다는 의미가 아니다.

## 다음 단계 / 남은 범위

- 기존 운영 저장소의 이미지 별도 저장 및 지연 로딩, metadata-only 조회와 페이지 단위 로딩.
- 원본 파일 선택을 유지하는 재개 가능한 보관 생성 및 저장 공간 사전 안내.
- 여러 월의 작은 색인을 함께 검색하고, 명시적 동일인 확인을 거친 월간 이력 연결.
- 보관 기록을 실제 운영 분석으로 가져올 때 과거 평가 보존과 날짜 정규화 처리.
- 실제 4GB RAM PC·누적 운영 데이터·사용자 지정 폴더 권한·저장 공간 부족 환경 검증.

## 검증

- TypeScript 검사 통과.
- 단위/회귀 검사: 75개 파일, 582개 테스트 통과. verify:fast 전체 통과.
- 배포용 Vite 빌드 통과.
- 신규 검사: 원문·이미지 보존, 변조 탐지, 손상 JSON 완료 차단, 취소, 덮어쓰기 방지, 저장 실패, 경로 제한, 2000건 sink 처리 시 반환 배열 비누적.
- 브라우저 검증은 `scripts/verify-local-archive-browser.mjs`에서 합성 자료·분리된 브라우저·외부 요청 차단으로 수행한다. 폴더 선택기는 OPFS로 대체하며 사용자 실제 폴더 권한 테스트는 아니다.
- 최종 빌드 브라우저 검사: 합성 180MiB/180건 저장·재연결·검색·선택 원문 조회·닫기 통과. 목록 27,928바이트, 수행 11초. V8 old-space 256MiB 제한 옵션을 사용했지만 전체 프로세스/RAM 상한이라는 의미는 아니다. 초기 시험 데이터 생성기가 전체 JSON 문자열을 메모리에 쌓는 문제가 있어 Blob 조각으로 생성하도록 변경한 뒤 통과했다.
- 실제 개인 자료는 저장소 밖에서 동일 writer의 Node 파일시스템 어댑터로 검증했다. 9월 173.1MiB/66건, 11월 389.7MiB/164건 모두 재읽기·해시 대조·원본 불변 확인 통과. Node 최고 RSS는 각각 약 181MiB, 190MiB였으며 실제 브라우저/저사양 PC 측정치는 아니다. 원본·변환 자료를 GitHub에 포함하지 않는다.
- 10월 246.3MiB/91건도 같은 검증 통과(Node 최고 RSS 약 190MiB). 세 보관함 합계 321건. 보관 사본은 추가 디스크 공간을 사용하며 원본을 자동 삭제하지 않는다.
