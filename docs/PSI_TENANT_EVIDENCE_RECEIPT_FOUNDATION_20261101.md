# NEW-PSI 10차 — 기업별 자필 원본 수신 원장 (검증용 기반)

## 현재 상태
- 설계·코드: **별도 브랜치/PR의 staging 기반**. 운영 DB에 테이블을 생성하거나 기존 데이터를 이전하지 않음.
- API: 기존 Vercel 함수 `/api/saas/access?resource=evidence-receipts` 재사용.
- 운영 기본값: `PSI_TENANT_EVIDENCE_ENABLED` 미설정이면 HTTP 503 (`TENANT_EVIDENCE_NOT_READY`).
- 이 기능은 `P03/P04`의 일부 기반일 뿐, 기존 근로자 `WorkerRecord`의 보존·승인·제출 체계 전체가 아님.

## 보안 아키텍처
1. 기업별 인증 사용자는 Supabase Auth `getUser`로 검증한다.
2. `X-PSI-Tenant-ID`에 대해 매번 활성 기업 소속을 재확인하며 owner/admin/reviewer만 허용한다.
3. 요청은 UUID `workerId`를 필요로 하며, DB 외래키 `(tenant_id,worker_id)`가 **신규 기업별 근로자 등록부**와 일치해야 한다.
4. 브라우저/요청으로 `received_at`·`received_by`를 입력할 수 없고, DB 삽입 트리거가 서버시각과 `auth.uid()`를 정한다.
5. 파일 원본은 최대 2 MiB의 **실제 바이트**로 보관한다. JPEG/PNG/WEBP/PDF 형식 검사, UTF-8 JSON 전체 크기 제한, 중복 요청 UUID 제한을 적용한다.
6. 기록 변경/삭제 SQL을 차단하는 트리거와 RLS, 컬럼별 INSERT 권한으로 우발적 변경을 차단한다. viewer/anon 및 다른 기업은 조회/등록 불가.
7. 서버가 업로드 당시 바이트와 재조회 당시 보관 바이트에서 SHA-256을 각각 계산해 응답하며 이미지 본문은 API에 반환하지 않는다.

## 여전히 남은 문제
- **운영 DB 적용 없음**: SQL은 `supabase/proposals/psi_tenant_evidence_receipts_staging.sql`에 저장했다. migration으로 간주하면 안 된다. Supabase CLI로 정식 마이그레이션을 생성하고 격리 DB에서 SQL/RLS/제약을 검증한 뒤 적용해야 한다.
- **기존 자필 자료 이관 안 함**: 2026년 2월 등 과거 기록을 이 원장에 지금 올리더라도 실제 서버 최초 수신시각은 **현재 등록시각**이다. 과거 작성시각을 증명하지 못한다.
- **현장별 권한 분리 없음**: 지금은 기업 `tenant_id` 단위다. 동일 기업 내 여러 현장 및 사용자 역할별 site_id 통제는 별도 설계가 필요하다.
- **공인 WORM/시점인증 아님**: DB 슈퍼유저/백업 운영자는 원리상 데이터를 변경할 수 있다. 트리거·RLS는 공인 타임스탬프·외부 독립 보관·법적 원본 인증을 대신하지 않는다.
- **보관기간/암호화 정책**: 개인식별 가능한 원본 이미지와 안전 기록이므로 저장 목적·사용자 권한·보존·삭제·백업 정책과 법무 검토가 먼저 필요하다.
- **운영 접근 제한**: 기존 PSI 공유 관리자 로그인으로 새 기업별 증빙을 저장하지 않는다. 개인 계정과 활성 소속만 인정한다.
- **클라이언트 연결 미완료**: 기본 UI로 자동 업로드·백그라운드 전송하지 않는다. 8·9차 로컬 ZIP과 신규 서버 원장은 별도이며 조인·대사 워크플로 미구현.
- **무료/용량 한계**: 2 MiB 원본을 DB bytea에 저장하므로 DB 저장공간·네트워크·보존 비용을 평가해야 한다. 대용량/대량 운영에는 버전·RLS가 적용된 별도 스토리지 설계가 필요하다.
- **초기 수신 후 제출**: 제출 승인·열람/반출 로그 및 파일 해시의 별도 시점 앵커는 아직 없다.

## 검증 계획
- 실제 PostgreSQL(PGlite)에서 두 기업/근로자 교차 접근, 익명·viewer·정지 소속 차단, 서버 수신시간 필드 변경 불가, INSERT 중복, 수정·삭제 트리거, 파일 용량 제약을 검사한다.
- API 가상 테스트에서 기본 503, 인증/역할 차단, 변조 시도, 매직바이트 검사, SHA-256 및 응답 비노출을 검증한다.
- 운영 전 별도로 실제 Supabase 테스트 프로젝트에서 회원 가입/기업 전환/원본 등록/관리자 재조회/퇴사·정지 사용자 접근 거부/원본 비교/백업 복구를 시험한다.

## 정식 적용 수용 기준
- 사전 준비: 업체·현장 권한 부여 절차, 원본 보관 동의 및 보존·파기 기준, 긴급 운영 복구·비용 한도.
- Supabase CLI `migration new`로 생성한 정식 migration 사용.
- 격리 프로젝트에서 migration·RLS test green, 보안 advisors 확인, 역할 별 API 실제 시험.
- 사용자 승인 없이 기존 원본을 소급 이관하지 않음.
- `PSI_TENANT_EVIDENCE_ENABLED=true`는 준비가 모두 확인된 후에만 설정.
- GitHub 같은 커밋 CI 및 Vercel READY, PC/Android 실제 테스트, 개인정보 유출 확인.

**현재 완료 판정: 시범 코드·격리 DB 테스트 준비. 운영 DB 적용/실사용은 미완료.**

## 2026-11-01 운영 DB 읽기 전용 확인
- Supabase 프로젝트 `PSI-Database`는 ACTIVE_HEALTHY 상태이고 기본 공용 스키마의 RLS가 활성화돼 있다.
- `psi_tenants`, `psi_tenant_memberships`, `psi_tenant_workers` 등 신규 테넌트 자료의 현행 조회 행수는 **0건**이다.
- `psi_tenant_evidence_receipts`는 운영 테이블 목록에 아직 없다.
- 위 조회는 저장소의 테이블 목록 메타데이터만 확인했다. 기존 근로자 자료·파일·실제 데이터에 대한 수정/이관은 실시하지 않았다.
- 실제 기업·계정 소속을 승인해 시험하기 전까지 `PSI_TENANT_EVIDENCE_ENABLED=true`를 설정하지 않는다.

## 보안·출시 검증 보충
- RLS에서 허용하지 않는 UPDATE/DELETE는 대상 행 0건으로 조용히 거부될 수 있다. 격리 테스트에서는 이를 성공 차단으로 판정하고, 바이패스 권한의 SQL에서는 별도 변경 차단 트리거가 작동하는지 확인한다.
- 현장별 `site_id` 범위와 원본 다운로드 열람 로그가 없으므로 신규 기능의 **기업별 보안 경계**만 일부 갖춘 상태다. 보안 검토 없이 여러 현장이 공유하는 운영 환경에 확장하지 않는다.
- 새 기능에 사용하는 `bytea` 저장 용량, 백업 비용과 개인정보 보존·삭제 정책을 승인받기 전까지 실자료 업로드는 금지한다.
